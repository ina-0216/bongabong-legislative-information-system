# TextBee OTP Setup

Updated: 2026-10-10

- For local setup, copy `server/.env.example` to the ignored `server/.env` and configure TextBee there. The municipality must set production credentials privately in its hosting account; never commit `.env` or place provider keys in client/mobile variables.
- The municipality privacy/data-protection owner has approved TextBee for resident phone numbers and OTP message content, as confirmed by the user.
- Production Render deployment is not set up yet. No TextBee account/device pairing, API key creation, Render service, or live SMS has been performed by this code change.
- A Render Blueprint is prepared at `server/render.yaml`, but it has not been applied or deployed. Connect the municipality-owned GitHub repository to Render and configure `server/` as the service root. The Blueprint currently selects a free API service and a private-network-only free Key Value Redis instance. `JWT_SECRET` is generated by Render, while `MONGODB_URI` must be supplied privately. Add `TEXTBEE_API_KEY` after TextBee account/device setup.

Before go-live, provision production services with persistent Redis, backups, and data-protection controls that meet municipal requirements; see [Render free-tier limitations](https://render.com/docs/free).

## TextBee account and Android phone

1. Create a TextBee account and verify its email.
2. Install the TextBee Android app from its official download page. TextBee currently distributes the Android app as an APK rather than through Google Play.
3. Keep an active SIM in the phone. Check that the SIM can send SMS and has the required carrier credit/plan.
4. In the TextBee dashboard, add a device and scan its QR code in the app. This pairing key is used by the phone; do not revoke it while the device is registered.
5. Grant the app SMS permission, select the SIM that should send, and set this phone as the default device. On Android 15+, allow restricted settings if SMS permission is blocked. Keep the phone powered, online, and exempt the app from battery optimization so Android does not stop its background connection.
6. Create a separate API key for the iBOSys backend. Treat this key as a secret. The optional device ID is an identifier, not an API credential.

TextBee relays sends through the paired Android phone and its SIM. A successful HTTP response means the message was accepted or pushed to the phone; it is not proof that the carrier delivered it. Keep the phone online and check TextBee's message status if an OTP does not arrive. TextBee expects recipient numbers in E.164 format; the backend converts accepted local Philippine `09…` numbers to `+639…`.

## Local development

In the ignored `server/.env`, set:

```dotenv
NODE_ENV=development
SMS_OTP_MODE=textbee
TEXTBEE_API_KEY=your_private_key
# Optional when TextBee has more than one device. Otherwise set a default in its dashboard.
TEXTBEE_DEVICE_ID=
TEXTBEE_BASE_URL=https://api.textbee.dev/api/v1
```

Start the backend, open the public consultation feedback form, and send a test OTP to a phone you control. Verify the message in TextBee's message history and enter the code in the form. The real OTP is not returned to the app or logged. Do not use the development `test` provider mode outside development/test.

## Render deployment

When the backend is deployed, enter connection secrets in Render's service **Environment** settings rather than in repository files. The prepared Blueprint generates `JWT_SECRET`, links `REDIS_URL` to the Redis instance, and prompts for the production `MONGODB_URI` ([Blueprint secret behavior](https://render.com/docs/blueprint-spec), [Render environment-variable documentation](https://render.com/docs/configure-environment-variables)).

Set at minimum:

```text
NODE_ENV=production
SMS_OTP_MODE=textbee
TEXTBEE_BASE_URL=https://api.textbee.dev/api/v1
MONGODB_URI=<enter privately in Render>
```

After pairing TextBee, add `TEXTBEE_API_KEY` in Render's Environment. Set `TEXTBEE_DEVICE_ID` only if you want to pin sends to a specific paired phone. Connect the municipality-owned GitHub repository to Render and apply the Blueprint through the municipality's hosting account. Keep all keys only on the server; never add them to `EXPO_PUBLIC_*` or any client/mobile variable. Add `FRONTEND_URL` and `PORTAL_URL` after those clients have deployed, and configure Cloudinary/email credentials if those features are needed.

The Blueprint sets the server directory as the service root, installs with `npm ci`, and checks `/api/health`. For the municipal deployment, provision an authorized cloud MongoDB database and allow only the Render service to connect; enter its URI privately in Render. Import or create municipal records only through the municipality's approved data-migration process. Confirm the service becomes healthy, then test only with an authorized phone. Do not test against residents' numbers without the required approval.

## Acceptance checks

- Missing TextBee API key returns a configuration error and does not leave a valid OTP in Redis.
- The backend sends the generated six-digit code to TextBee using the secret `x-api-key` header and an E.164 recipient.
- TextBee errors fail the OTP request cleanly and do not leak the provider key or OTP into API responses/logs.
- A TextBee queue acceptance returns the existing five-minute OTP response shape; a real phone test confirms end-to-end delivery.
- Existing PhilSMS, Semaphore, and development-only test modes continue to work.
